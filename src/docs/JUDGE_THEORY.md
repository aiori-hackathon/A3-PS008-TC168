# PS-008 theory and judge preparation

This guide explains the ideas behind the project from first principles to the design decisions a judge is most likely to ask about. The project is a deterministic network-configuration agent: it accepts a structured intent, builds a candidate change, proves its effect in a software twin, waits for human approval, and only then commits the change.

## 1. The problem in one sentence

Changing a route is not just writing a command. A safe agent must answer four questions:

1. Is the request well-formed and authorized by the supported policy?
2. What exact command would be executed?
3. What forwarding behavior would change, including loops or lost reachability?
4. Can the change be applied atomically, verified, and reversed if anything fails?

The application separates planning from execution so that a preview never changes the lab.

## 2. Networking fundamentals

An IPv4 route maps a destination prefix to a next hop or a connected interface. A prefix such as `10.20.0.0/24` contains addresses whose first 24 bits match the network. Routers choose the longest matching prefix: `/24` is more specific than `/16`, and `/16` is more specific than `/8`.

The twin contains three routers:

- R1 owns `10.10.0.0/24`.
- R2 owns `10.30.0.0/24`.
- R3 owns `10.20.0.0/24`.
- R1-R2 uses `10.0.1.0/24`; R2-R3 uses `10.0.2.0/24`.

R1 initially cannot reach the engineering LAN on R3. Adding `10.20.0.0/24 via 10.0.1.2` makes the path R1 -> R2 -> R3. The next hop is valid only if it is on the source router's directly connected link; otherwise the command is rejected before deployment.

## 3. The software twin

The digital twin is a small executable model of topology and forwarding tables. It is deliberately narrower than IOS: it models static and connected IPv4 forwarding, not hardware, timing, dynamic protocols, packet loss, or real device access.

For a trace, the twin repeatedly:

1. Finds all routes containing the destination address.
2. Selects the longest prefix, preferring connected routes on an equal prefix.
3. Stops successfully when the destination is on a connected network.
4. Fails on a missing route, invalid adjacency, or repeated router.

The repeated-router check is the basic loop detector. Validation also partitions the requested prefix at every relevant route boundary and probes each interval. This matters because testing only one address can miss a more-specific route that changes behavior for part of a prefix.

## 4. Intent, normalization, and command generation

The public input is a structured intent, not an arbitrary shell command. The supported intents are `add_static_route` and `remove_static_route`; the supported protocol is IPv4 static routing. Input is normalized with strict IPv4 network parsing, router allowlisting, neighbor checks, and bounded identifiers/reasons.

The command is generated by the server from the normalized intent. The client cannot submit a replacement command, failure mode, or candidate object. At the deployment boundary the command is reconstructed and checked against the canonical IOS-style allowlist again. This is defense in depth: validation protects planning, while the second check protects execution.

## 5. Review as a capability and a state machine

Preparation creates a review containing the normalized request, exact command, current lab revision, integrity fingerprint, forwarding evidence, and expiry time. It does not apply routes.

The lifecycle is:

`pending -> deployed`

or one of the terminal outcomes:

`rejected`, `expired`, `stale`, `invalid`, `failed`, or `rolled_back`.

Approval is accepted only when the review is pending, unexpired, tied to the current revision, and still has the same fingerprint. The service reloads state under a lock and revalidates before applying. Therefore a stale browser page or a second approval cannot silently overwrite a newer commit. A review is single-use.

This is similar to optimistic concurrency control: the revision and fingerprint are the version check, while the state lock serializes the commit.

## 6. Transaction safety and rollback

Deployment writes a journal containing the complete pre-change state before mutation. It applies the route, verifies the expected postcondition, increments the revision, records audit evidence, atomically replaces the state file, and removes the journal.

If applying or verifying fails, the previous routes, revision, and applied-request IDs are restored while the failure evidence remains in the audit trail. If the process stops while a journal is pending, the next load detects it and recovers conservatively. This is why the project can claim rollback and crash-recovery behavior rather than merely catching an exception.

## 7. Persistence and isolation

The CLI and web interface use the same service and persistence rules. The state file records the version, revision, routes, applied IDs, reviews, and audit. Version 1 state is upgraded compatibly on the next write.

Each browser demo session gets its own state file under the demo directory. A demo reset therefore cannot mutate another session's lab or the persistent lab. Mutating HTTP requests also require the expected same-origin and session CSRF protections.

## 8. Why the agent is working nicely

Within its declared scope, the design is strong because it has all three safety layers:

- **Before execution:** strict schema validation, topology validation, reachability probes, conflict checks, loop checks, and human-readable evidence.
- **At execution:** current-revision and fingerprint checks, locking, command allowlisting, and a fresh revalidation.
- **After execution:** postcondition verification, atomic persistence, audit evidence, and rollback/recovery.

The current automated evidence is 84 passing pytest tests covering core logic, review races, persistence, API security, demo isolation, and browser-facing behavior. Browser checks cover desktop and mobile flows, approval/rejection, invalid changes, rollback, verification failure, reload, keyboard access, and workspace isolation.

## 9. Likely judge questions and strong answers

### What makes this an agent rather than a form that writes commands?

It interprets a structured intent, reasons over a network model, generates a candidate, explains forwarding impact, validates safety properties, requests explicit approval, executes transactionally, verifies the result, and records the outcome. The deterministic model is intentional: a network controller should be predictable and auditable.

### Why not let the user enter a raw IOS command?

Raw commands make it difficult to validate intent, prove impact, or prevent injection. The user chooses a supported change; the server generates the exact command and checks it again at the deployment boundary.

### How do you detect routing loops?

A trace records visited routers and rejects a repeated router. Preview validation probes every forwarding interval created by relevant prefix boundaries, so a loop hidden behind a more-specific route is also detected.

### What happens if the state changes after preview?

Approval compares the review's revision and fingerprint with the current state, reloads under the lock, and revalidates. The review becomes stale instead of applying against a different topology.

### Can a user approve twice or approve a modified candidate?

No. Terminal reviews are single-use, and the candidate fingerprint is checked again. The approve endpoint accepts a review ID, not a client-supplied command.

### What happens if deployment fails halfway through?

The journal preserves the complete before-state. Failure restores routes, revision, and applied IDs, while preserving failure evidence. A leftover journal is recovered on the next load.

### Why does route removal produce a warning instead of always failing?

Removal can be an intentional change that loses reachability. The system makes that consequence explicit in the review so the operator can reject it or approve it knowingly. A removal that reveals a forwarding loop is rejected.

### Is this connected to real routers?

The simulator is a local software twin and does not emulate IOS. The separate GNS3 adapter can connect to configured IOS-compatible devices over verified-host-key SSH, but the current repository milestone has only fake/offline validation because no real lab was available. Do not claim device-observed success until the dashboard shows actual router read-back and configured probe evidence. It is not a production controller or tamper-proof compliance system.

### What are the main limitations?

The model covers fixed IPv4 static forwarding only. It does not model dynamic routing, IPv6, bidirectional application sessions, hardware behavior, packet timing, or a tamper-proof compliance log. Mentor confirmation of the provisional intent pair is still required.

## 10. A concise live demonstration

1. Open **Judge demo** and choose **Add route**.
2. Show that the preview changes the R1 trace but not the current state.
3. Point to the generated command, validation checks, and before/after path.
4. Approve and deploy; show the revision and audit event change.
5. Try **Conflict** or **Loop** and show that deployment is blocked.
6. Try **Rollback** or **Verification failure** and show that the state returns to its prior revision while evidence remains.
7. Explain that CLI and web use the same service, so the safety rules are not UI-only.

## 11. Honest conclusion

The project is a safe, review-first prototype for deterministic static-route changes. Its strongest contribution is the complete control loop—intent, evidence, approval, atomic deployment, verification, rollback, and audit—not a claim that a local simulator is a production network controller.
